## SYNTHESIZE

### Pairing: HUD ↔ BLACKWAVE

The trust model is sound in principle: BLACKWAVE owns all device authority, signing, and radio configuration. HUD is a capability-aware consumer surface that fetches a role manifest and displays fleet status. The role manifest gates which capabilities the HUD advertises, not what it can execute.

**But the gap between advertised capabilities and implementable commands (H5) is the central architectural risk.** The `scopeToCapability` map projects 12 scopes into capabilities, but only 2 commands exist. A user who enables BLACKWAVE HUD mode sees `radio.configure`, `device.reboot`, `ota.apply` in their capability list — these appear as permissions they hold. The distinction between "the bridge says I'm allowed to" and "the HUD can actually do it" is not surfaced anywhere. This is not an authorization bypass (the commands don't exist, so they can't be invoked), but it is a **trust-display integrity problem**: the capability list is a lie of omission. A security-conscious user reading their capability list would reasonably conclude they have reboot authority when they don't.

**The blocking-I/O-on-coroutine pattern (H2) is the central operational risk.** `isAvailable()` + `fetchRole()` are synchronous HTTP calls executed on `Dispatchers.IO`. The polling loop runs every 30s with no backoff. If the bridge is unreachable, each cycle burns 5s (connect timeout) × 2 calls = 10s of blocked IO thread time. With 4 endpoints and retry behavior, a single poll cycle can block for 20-40s. Android's IO dispatcher default pool is small (64 threads on most devices, but shared with all coroutines). Under concurrent load (other plugins, UI coroutines), this causes thread starvation and UI jank.

### Pairing: BLACKWAVE ↔ Cardputer

Unassessable from provided excerpts. The BLACKWAVE catalog (`load_catalog()`) determines which devices are supported. If the Cardputer's model ID isn't in the catalog, `/mobile/v1/devices/{model_id}` returns 404 — correct rejection. If it is enrolled, the fleet endpoint shows `enrollment: "enrolled"` but all telemetry is `"NOT REPORTED"` — the bridge projects catalog metadata, not live device state. This means the Cardputer's actual firmware state (running DEMON//SIGNAL, not BLACKWAVE) is invisible to the HUD through this path. The HUD would see a catalog card, not a live device.

The mobile gateway's `pathfinder_projection` function (line 405) demonstrates the intended architecture: "Reticulum routes. BLACKWAVE authorizes. BLE pairing is not enrollment." If a similar projection exists for the Cardputer, it should explicitly state that the device runs non-BLACKWAVE firmware and that BLACKWAVE authority is limited to enrollment/catalog metadata, not runtime control.

### Pairing: HUD ↔ Cardputer (direct)

No direct path exists in the provided code. The HUD communicates only with the BLACKWAVE bridge. The Cardputer would need to report to the bridge (or a Reticulum instance on the bridge host) for the HUD to see it. There is no BLE-direct or USB-direct path from HUD to Cardputer in this architecture. This is the correct separation — the HUD should not bypass the authority layer.

### All Three Together

The intended trust flow is:

```
Cardputer (local firmware, no BLACKWAVE authority)
    ↓ enrollment/catalog only (no live telemetry path shown)
BLACKWAVE bridge (authority, signing, radio policy)
    ↓ role manifest + cached projections (HTTPS, Bearer auth)
HUD Android (display surface, capability-aware, no write authority)
```

**The architecture is correct: authority is centralized, display is delegated, enable ≠ authorize.** The role manifest is the enforcement boundary — the HUD can only show what the manifest permits. But:

1. **Transport security is the weakest link.** (H1) No visible TLS trust management for LAN certs. If HTTP is used, Bearer tokens are cleartext on the wire. If HTTPS with self-signed certs, no TOFU implementation is visible. This is the single most likely exploitable path: credential interception on the LAN.

2. **Pairing is an unauthenticated credential-return endpoint.** (B1) `/mobile/v1/pairing/complete` returns credentials with no `authorize` dependency. The security of the entire system rests on `pairing.complete()` correctly validating the request_id and nonce. Without seeing that code, this is an unverified trust root.

3. **Replay attacks are unmitigated.** (B2) No nonce/timestamp in the auth flow beyond the initial pairing. A captured Bearer token is valid until expiry with no revocation signal visible.

4. **The capability/command gap undermines trust display.** (H5) 10 of 12 advertised capabilities have no command implementation. This doesn't create a security hole but it creates a false sense of authority that could mislead an operator during an incident.

## REFLECT

### What's Right

- **Default-deny posture on RF and location** (B11, B12): radio disarmed, GNSS blocked, precise coordinates null. Correct.
- **Authority separation**: HUD never signs, never configures radios, never applies OTA. The bridge owns all write authority.
- **OTA is a no-op from the HUD side** (B10): `accepted: False`, `success: False`. The HUD can request but cannot commit.
- **Redirect-following disabled** (H1 comment): prevents silent HTTP→HTTPS upgrade hijacking. Good defense.
- **URL-encoding device IDs** (`URLEncoder.encode` in `fetchDeviceStatus`): prevents path injection.
- **Server validates model IDs against catalog**: unknown models return 404/422. Defense in depth.
- **`observed()` invariant**: forces explicit live/cached labeling. Honest about what's real vs projected.

### What's Missing

1. **TLS trust management** — The #1 gap. No TrustManager, no certificate pinning, no TOFU store visible on the Android side. The server side has no TLS configuration (delegated to uvicorn/proxy, invisible). This needs an explicit, documented trust model: either (a) pin the gateway's SPKI hash from `pairing.complete()` response (the field exists: `gateway_spki_sha256`), or (b) use a local CA with the cert installed in the Android trust store. The `gateway_spki_sha256` field is returned at pairing but never consumed by the client in the provided code.

2. **Replay protection** — Bearer tokens are stateless on the client. The server should implement either short TTLs with refresh, or a nonce-based challenge-response. Without seeing the pairing module, I can't confirm TTL is enforced.

3. **Per-entry inbox authorization** — Any paired client reads any inbox entry. If the inbox contains device-specific logs or captures, this is an over-broad read. The `model_id` in the ingest payload isn't checked against the authenticated client's authorized devices.

4. **Cardputer assessment** — Not possible without firmware excerpts. The architecture assumes the Cardputer is a catalog-only entry with no live telemetry. If the firmware has any network surface (LoRa mesh, BLE, serial), its interaction with BLACKWAVE authority needs its own review.

5. **Structured concurrency in PluginManager** — (H9) Child scopes escape parent lifecycle. On app shutdown, if `parentScope.cancel()` is called, plugin scopes survive because `SupervisorJob()` replaces the parent `Job`. Plugins must be individually stopped via `unregisterAll()`. If the app crashes, plugin coroutines may outlive the expected shutdown.

### Minimal Architecture Recommendation

The existing architecture is close to correct. Three concrete changes would close the main gaps:

1. **Wire `gateway_spki_sha256` into the client.** The pairing response already returns it. Store it after pairing and use it to pin the TLS certificate in `BlackwaveBridgeClient.get()` via a custom `TrustManager` that compares the server cert's SPKI against the stored hash. This gives TOFU without a CA and prevents MITM after first pairing.

2. **Add `withContext(Dispatchers.IO)` to all `get()` calls** (or migrate to OkHttp with async callbacks). This stops blocking the coroutine dispatcher and makes the suspend functions actually suspending. Add exponential backoff to the polling loop: start at 30s, back off to 5min on consecutive failures, reset on success.

3. **Collapse the capability list to match implemented commands.** Either implement the 10 missing commands (with server-side enforcement) or remove them from `scopeToCapability`. If they're future placeholders, gate them behind a `CapabilityTier.TIER_2` or `CapabilityTier.EXPERIMENTAL` flag so the UI can distinguish "available" from "actionable."
