1: # ADR-020: Android controller remains in the BLACKWAVE monorepo
2: 
3: - **Status:** Accepted for Phase 1
4: - **Date:** 2026-08-31
5: - **Scope:** Android foundation placement and protocol migration boundary
6: 
7: ## Context
8: 
9: The mission describes a logical split between `protocol/`, `android/core`,
10: `android/transport`, `android/domain`, `android/feature`, simulator and tools.
11: The repository audit found an established BLACKWAVE monorepo at
12: `/home/parrot/repos/fr3k-blackwave`, with firmware, bridge, schemas, WebUI,
13: release evidence and an existing Android client under
14: `apps/android-companion/`. The current client is intentionally a client of the
15: BLACKWAVE bridge and already documents that it does not own fleet identity,
16: signing, registry, OTA, revocation or Hermes state.
17: 
18: The current shared protocol authority is not protobuf/Buf. It is the existing
19: `blackwave-device/2` JSON event contract plus `fr3k-blackwave-peer/1`,
20: `fr3k-blackwave-ota/1` and FR3KCFG2 implementations. The repository contains
21: substantial dirty work from the operator, so gratuitous consolidation or
22: branch-wide migration would risk destroying unrelated changes.
23: 
24: ## Decision
25: 
26: Keep the Android controller in `apps/android-companion/` within the existing
27: BLACKWAVE monorepo. Introduce logical boundaries incrementally using Android
28: modules or packages only when each boundary has a tested contract and does not
29: duplicate an existing authority. Add a canonical language-neutral protocol
30: package only after an explicit field-by-field mapping and compatibility vectors
31: exist for the current contracts.
32: 
33: The first Android network path remains the existing authenticated gateway
34: projection. Direct LAN/BLE/USB transports may be added behind BLACKWAVE-owned
35: interfaces; they must not bypass the existing authorization, identity, audit or
36: recovery model. The app remains a client and cache, not a second registry.
37: 
38: ## Alternatives rejected
39: 
40: 1. **Create a new Android repository immediately:** rejected because it would
41:    duplicate current authority and lose the existing app/gateway evidence.
42: 2. **Replace current JSON/C++/Python contracts with protobuf immediately:**
43:    rejected because no complete field mapping, compatibility vectors or
44:    generated consumers exist yet.
45: 3. **Consolidate firmware and gateway repositories:** rejected because existing
46:    physical repository boundaries and dirty work are active evidence.
47: 
48: ## Consequences
49: 
50: - The mission's target logical architecture is a migration target, not a
51:   reason to fork working semantics.
52: - The existing Android module must be upgraded in controlled slices; current
53:   behaviour stays covered while new domain/transport contracts land.
54: - A protocol conformance harness and golden vectors become a prerequisite for
55:   any canonical protobuf/CBOR migration.
56: - Physical validation remains separate from build/unit/emulator evidence.
57: 
58: ## Verification gate
59: 
60: Before introducing a new canonical protocol package, record:
61: 
62: 1. authoritative source fields and owners;
63: 2. additive compatibility mapping;
64: 3. unknown-enum/unknown-field behaviour;
65: 4. cross-language golden vectors;
66: 5. Buf breaking-change policy;
67: 6. licensing and redistribution review;
68: 7. adapter tests against existing bridge and at least one simulator/physical
69:    capture where applicable.
